# مسار Build-Only — جاهز، ومحجوب بقيد منصة

## الحالة: الكود كامل ومُختبر، والتشغيل محجوب

الملف `.github/workflows/windows-build-only.yml` موجود على الفرع، مفحوص، ومُدرج في
قائمة الـworkflows المُراجَعة. لكن GitHub **لا يسمح** بتشغيله.

## السبب الدقيق (قيد منصة، لا خطأ في الإعداد)

توثيق GitHub لـ`workflow_dispatch` ينص حرفيًا:

> This event will only trigger a workflow run if the workflow file exists on the
> default branch.

الفرع الافتراضي للمستودع هو `main`. الملف موجود على
`arena/56e71924-erp-kayan` فقط. لذلك:

```
$ gh workflow run windows-build-only.yml --ref arena/56e71924-erp-kayan
HTTP 404: Not Found .../actions/workflows/windows-build-only.yml
```

الملف موجود فعلًا على الفرع (10,432 بايت، مؤكد عبر API)، لكن GitHub لا يسجّله
كـworkflow قابل للتشغيل ما دام غير موجود على `main`.

## ما لا أفعله

- **لن أدفع إلى `main`.** أمرك: لا تستخدم `main` كفرع عمل.
- **لن أفتح PR وأدمجه.** أمرك: لا Merge.
- **لن أُضيف trigger آخر** (`push`, `pull_request`) للالتفاف على القيد: ذلك يخالف
  «تشغيل يدوي فقط» الذي طلبته صراحةً، ويجعل المسار يعمل تلقائيًا.

## الحلول المتاحة — تحتاج قرارك

| # | الخيار | يخالف أمرًا؟ |
| --- | --- | --- |
| ١ | إيداع الملف في `main` (كوميت واحد يحتوي الملف فقط) | **نعم** — لا تستخدم `main` |
| ٢ | دمج PR #77 (فعندها يصل الملف إلى `main`) | **نعم** — لا Merge |
| ٣ | فتح PR صغير مستقل يحتوي الـworkflow فقط، ومراجعته ودمجه | **نعم** — لا Merge |
| ٤ | إضافة trigger مؤقت (`push` على هذا الفرع)، ثم إزالته | لا يخالف نصًا، لكنه يخالف **قصد** «يدوي فقط» |

**توصيتي:** الخيار ٣ — PR مستقل صغير لملف واحد، تراجعه أنت وتدمجه إن أقررت.
هذا هو أقل مساس بأوامرك: لا أدفع إلى `main` مباشرة، ولا أدمج أنا.

## ما هو مُثبت الآن بلا تشغيل

| الضمانة | كيف أُثبتت |
| --- | --- |
| تشغيل يدوي فقط | اختبار يفشل عند إضافة `push:` — تحقق عكسي 11/1 |
| قراءة فقط، لا نشر | اختبار يفشل عند `contents: write` — تحقق عكسي 11/1 |
| لا بيئة محمية | لا يوجد `environment:` في أي job |
| لا تثبيت ولا إعادة تشغيل | لا `VERYSILENT` ولا `Restart-Computer` ولا `Start-Process` |
| لا مفاتيح خاصة | مفتاح عام واحد مُثبَّت؛ ذكر واحد لـ`PRIVATE KEY` وهو فحص التسرّب |
| الاستخراج بـ`innoextract` | مثبت في الخطوة، مع بناء المُستخرِج وطباعة هاشه |
| رفض الملفات الفارغة | `[ ! -s "$file" ]` يعدّها مفقودة |
| رفض حزمة تحمل مفتاحًا خاصًا | `grep` على `BEGIN .*PRIVATE KEY` ثم `exit 1` |
| الحماية الأصلية لم تُمَس | `windows-installer.yml` بلا أي تعديل |

## ما يفعله عند التشغيل

1. يبني `KAYAN-ERP-Setup.exe` بالمفتاح العام المُثبَّت.
2. يبني `innoextract` من المصدر المُثبَّت ويطبع هاشه.
3. **يستخرج** الحزمة — لا يثبّتها.
4. يشغّل `verify-extracted-windows-installer.mjs` بقائمة الإلزام الكاملة.
5. يعدّ `migration.sql`، ويبحث عن `node.exe`, `pg_ctl.exe`, `pg_dump.exe`,
   `pg_restore.exe`, `RepairTool.exe`, `erp_kayan.exe`.
6. يرفض أي ملف بحجم صفر.
7. يرفض أي مفتاح خاص داخل الحزمة.
8. يرفع الـSetup وتقرير الفحص كـArtifacts مع SHA256 والكوميت.
9. يُعلن صراحةً ما لم يُثبته.
