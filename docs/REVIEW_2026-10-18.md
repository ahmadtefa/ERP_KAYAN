### منح المحاسب الافتراضية

منح modules: accounting وparties وinventory وreports، مع قراءة فواتير البيع والشراء فقط من هذين المجالين. هذا يعني أن المحاسب **ليس read-only عمومًا**؛ قد يملك إنشاء/تعديل الحسابات وترحيل القيود وإدارة المخزون وفق كتالوج هذه الوحدات. لا يمنح إدارة المستخدمين أو إنشاء/ترحيل الفواتير افتراضيًا. المنح قابلة للتخصيص وفق قيود الأدوار النظامية.

### تحقق الخادم والإصلاحات

1. RateLimitGuard ثم JwtAuthGuard ثم PermissionsGuard مسجلة عالميًا.
2. JWT يُتحقق من توقيعه وصلاحيته، ثم نشاط المستخدم وحذفه والشركة وtokenVersion.
3. أُضيف جلب الصلاحيات وSuper Admin والفروع النشطة من DB لكل طلب، مع استبعاد أدوار الشركات الأخرى والمحذوفة؛ إلغاء المنح لا ينتظر انتهاء JWT.
4. ImportController وExportController ينفذان checks ديناميكية للنوع. أُصلح bypass في import upsert: يحتاج صلاحية update المناسبة بالإضافة إلى create للعملاء/الموردين/الأصناف.
5. أُضيف SuperAdminGuard إلى كامل FullBackupController: منح `admin.backup` لموظف شركة لا ينبغي أن يتيح تحميل أو استرجاع كل قاعدة البيانات بجميع الشركات.
6. اختبار guard مباشر، وعزل tenant في auth، ومنع التصعيد، وكتالوج setup، وقيود upsert، وربط guard بالـcontroller مغطاة باختبارات وحدة.

### حدود واضحة / ما لم يكتمل إثباته

- لا يوجد فصل موحد read/create/update/delete لكل شاشة وعملية؛ كثير من المجالات تستخدم manage/post. لم أغيّر نموذج الصلاحيات إلى نموذج جديد.
- يوجد جدول `UserPermission` في schema، لكن تجميع المنح في auth الحالي مبني على الأدوار؛ لا نعد المنح المباشرة للمستخدم ميزة فعالة مكتملة.
- `reports.print` و`sales.print` و`admin.backup.restore` و`admin.users.password` موجودة في الكتالوج، لكن بعض endpoints الحالية تستخدم read/manage/admin.backup بدل فصل هذه العمليات بتلك الأكواد. وجود الكود في الكتالوج لا يثبت تطبيقه على كل المسارات.
- عرض/إخفاء الأزرار ليس بديلًا عن تحقق الخادم، ولا يوجد إثبات اختبار واجهة شامل لكل دور ولكل زر.
- لم تُنفذ مراجعة اختراق شاملة أو اختبار HTTP لكل توليفة role/company/branch. اختبارات الوحدة لا تكفي وحدها لذلك.
- المنح الموجودة سابقًا في قواعد عملاء فعلية لا تتغير تلقائيًا بمجرد إصلاح setup؛ لم أعدل قاعدة بيانات مستخدم أو أفترض أن setup يعمل كترقية أدوار.

## 4. Excel / PDF / الاستيراد / الاسترجاع / التكلفة والمرتجعات

### Excel وPDF

- `writers.ts`: ملفات XLSX حقيقية عبر ExcelJS، وCSV مع BOM للعربية، وصفحة طباعة HTML RTL/LTR مع تفاصيل الشركة والشعار. اختبارات workbook تقرأ الخلايا وأنواعها والعناوين وتفاصيل الشركة.
- `ListTablesService`: العملاء والموردون والأصناف والمخزون والفواتير والقيود ودليل الحسابات والفترات والمستخدمون والأدوار وaudit والنقدية والتحويلات.
- `DocumentsService`: فاتورة بيع/شراء، أمر بيع/شراء، سند نقدية، قيد يومية. للتصدير checks قراءة + تصدير حسب نوع المستند؛ بعض تصدير القوائم يعتمد صلاحية القراءة فقط.
- PDF يعتمد متصفح Chrome/Edge/Chromium مثبتًا على الخادم. capabilities يصرح بتوفره؛ عند عدمه تتاح الطباعة والحفظ PDF عبر المتصفح بدل ادعاء توليد PDF على الخادم.
- لا دليل حتى الآن على اختبار بصري لكل PDF عربي/كل مستند على جهاز Windows نظيف. كما لم تُضف هنا إعادة تصميم للقوالب أو UI.

### استيراد البيانات المحاسبية

- XLSX/CSV، قوالب، أسماء أعمدة ثنائية اللغة، dry-run، أخطاء الصف والعمود، ومعاملات تمنع الكتابة الجزئية.
- الأنواع الحالية: customers، suppliers، items، chart-of-accounts، opening-balances. ليس استيرادًا عامًا لكل الفواتير والقيود التاريخية.
- دليل الحسابات: parent-first، التكرارات، وتحويل الحساب الأب إلى grouping وفق القيود.
- الأرصدة الافتتاحية: تحقق توازن المدين/الدائن، حسابات صالحة، منع صنف مخزني مكرر، draft للمراجعة لا auto-post، warehouse/branch scope، وreplay idempotency.
- اختبارات وحدة تغطي الحالات السابقة؛ السيناريو الحقيقي في التشغيل التشخيصي نجح في كل فحوص الاستيراد الوظيفية، وكان فشل login assertion فقط قبل إصلاحه.

### النسخ الاحتياطي والاسترجاع

- Company JSON backup/inspect/restore مع بيانات الشركة والشعار، remap identifiers عند الحالة المسموح بها، child/parent dependency ordering، معاملة واحدة، وحماية من ملف ناقص يمحو جداول موجودة.
- actor/audit links تعالج قبل حذف المستخدمين، وسجل purge/restore داخل المعاملة؛ إصلاح branch القديم للعلاقات موجود بالفعل.
- الملف DUMP لا يمر بوصفه JSON: يُرفض برسالة توجه إلى full restore.
- Full PostgreSQL backup: pg_dump/pg_restore وأرشيف custom، safety backup، تأكيد الاستبدال، maintenance/recovery وآلية الاحتفاظ. أصبح الوصول إليه Super Admin فقط.
- اختبار restore الحقيقي للـdemo إلى قواعد PostgreSQL نظيفة مستقل داخل CI، ولم نعتبر تحقق JSON syntax أو اختبارات mock بديلًا عنه.
- حماية العملية أثناء الاستعادة لا تعني سياسة نسخ خارج الجهاز أو تشفير backup at rest أو خطة disaster recovery مختبرة خارج CI؛ لم تُضف هذه هنا.

### تكاليف المشتريات الإضافية والمرتجعات

- أكثر من charge مسمى (مثل Freight/Insurance) مع إجمالي محفوظ في فاتورة الشراء.
- التوزيع حسب قيمة السطور، fixed-point BigInt لأربع منازل وطريقة أكبر البواقي؛ مجموع التوزيع يساوي التكلفة بدقة، مع رفض القيم السالبة أو الأساس الصفري غير الصالح.
- تكلفة المخزون تتضمن landed cost، والمرتجع يعيد القيمة/الضريبة/تكلفة المخزون المرتبطة بالأصل بدل استخدام متوسط متغير وقت الإرجاع.
- cumulative returned quantities/net/tax/cost تمنع تجاوز الأصل وتضع بقايا التقريب في آخر مرتجع جزئي؛ عكس المرتجع يحرر المتراكمات.
- منع استخدام endpoints المرتجعات لفاتورة عادية، ومنع عكس أصل عليه مرتجعات منشورة، وحماية stock quantity حتى عندما cost=0، وحجز صفوف أثناء العمليات الحساسة.
- اختبارات وحدة تغطي التوزيع، landed purchase posting، المرتجعات الجزئية والكاملة والعكس والـzero-cost stock. السيناريو الحقيقي للمرتجعات يُشغّل قبل المحاسبة ضمن PostgreSQL CI.
- لم يُضف حساب تلقائي لرسوم جمركية من تعريفة خارجية أو أسعار صرف متعددة أو سياسة توزيع حسب الوزن/الحجم؛ التنفيذ الحالي حسب القيمة.

## 5. الاختبارات والإصدار

### ما لا يحتاج إعادة تنفيذ

- أسباب Flutter عولجت: constructor key، callback map ذو الوسيط المسمى، النوع الناتج، import غير مستخدم وDropdown deprecated value. فشل widget test كان بسبب استهداف TextField بترتيب يشمل حقول رأس الفاتورة؛ أصلح بمفاتيح محددة دون تغيير المتوقع.
- branchId في السيناريو المحاسبي صُحح إلى principal.branchId، وكذلك توقع HTTP 201 لتسجيل الدخول. كل سيناريوهات PostgreSQL والاستيراد والصلاحيات والاسترجاع نجحت فعليًا في التشغيل المشار إليه.
- JwtAuthGuard يقرأ isSuperAdmin وuserRoles/rolePermissions والفروع وtokenVersion من DB، ويقارن tokenVersion بالـJWT؛ AuthService يضع النسخة في login وrefresh. لا إعادة كتابة لهذه الآليات.
- setup يستخدم PERMISSIONS المركزي، ويمنح ACCOUNTANT وحدات accounting/parties/inventory/reports وقراءة الفواتير فقط، وينشئ الفترة المالية والمخزن الافتراضي. اختبارات الوحدة وHTTP موجودة واجتازت CI.

### الإضافة المحدودة لهذا الاستكمال

توسيع smoke test الموجود على Windows فقط، دون استيراد Excel جديد أو تغيير التطبيق أو UI:

1. إنشاء customer sentinel عبر API الخاص بالتطبيق المثبت.
2. تنزيل JSON backup، ثم تغيير sentinel والتحقق من تغيره، واسترجاع الملف عبر multipart، وإعادة تسجيل الدخول والتحقق من رجوع القيمة الأصلية.
3. إنشاء full PostgreSQL backup والتحقق من محتواه بـpg_restore وتنزيله وفحص PGDMP، ثم تغيير sentinel والتحقق منه، واسترجاع full backup مع safety copy، وإعادة تسجيل الدخول والتحقق من القيمة الأصلية.
4. لا تصدر إشعارات النجاح ولا يرفع المثبت إلا بعد اجتياز هذه الخطوات؛ نجاح a775f55 ليس بديلًا عن نتيجة هذه التغطية الجديدة.

هذه اختبارات بيانات CI مؤقتة فقط؛ لا تُستخدم قاعدة عميل فعلية ولا تُحذف فروع أو ملفات عمل. النتائج الخاصة بالتغطية الجديدة تُسجل في ملحق التحقق النهائي بعد انتهاء CI، ولا تُستنتج من مراجعة PowerShell محليًا.
