1. ~~workflow المسمى Windows build only **يبني Setup فعليًا** رغم الاسم؛ يستدعي build:clean غير الموجود.~~ **عولج:** `build:clean` معرّف الآن ويعمل، ويحرسه اختبار في `safe-checks.yml`. يبقى التحذير قائمًا: هذا الـworkflow **يبني Setup كاملًا** رغم اسمه، فلا يُستخدم كطريقة «تطبيق فقط»؛ لذلك أُضيفت `windows-app` لبناء التطبيق وحده.
2. build-installer.ps1 يفحص سياسة البناء والمفتاح العام الصحيح قبل التجميع. لم تُختبر متطلبات المفتاح/حمولة المنتج/الأدوات على جهاز البناء الحالي، ولا يجوز تجاوز السياسة.
3. بوابة اختبار المثبت والبيئة المعتمدة منفصلتان عن بناء التطبيق. لا يُحوّل إخفاق/غياب إثبات VM إلى نجاح، ولا يستعاض عنه بـCI عادي.
4. لا تحقق مثبت للتثبيت والترقية وخدمات PostgreSQL/Backend والتشغيل التلقائي والتوافق offline مع Win10/11 وصلاحيات مجلدات البيانات وcontrol schema.
5. لا إصلاحات في هذه المهمة لمسار البناء القديم، ولا موافقة مفترضة على إنشاء أو نشر Installer.

### الحد الأدنى لتجربة معزولة آمنة دون انتظار كل تحسين

| الترتيب | المطلوب من الخطة الأصلية | دليل الإغلاق |
|---|---|---|
| 1 | حسم P0 للجلسات، وفحص سلبي موجّه للعزل والأسعار، ومنع السالب والتكرار في المسار المراد تجربته | اختبارات موجّهة على القاعدة الحقيقية، دون إعادة حزمة ثابتة بلا سبب |
| 2 | تثبيت مصدر بناء واحد من Work وتشغيل بناء تطبيق Windows فقط | SHA واحد لـUI/API ونتيجة flutter build windows، دون خلط رؤوس PR #84 |
| 3 | التأكد من دخول المستخدم وفتح المخازن والمراجع وحفظ/ترحيل مستند مخزني بسيط بالأدوار المطلوبة | تجربة أساسية على بيانات اصطناعية؛ لا حاجة لإغلاق كل P2 أولًا |
| 4 | تحضير Setup متكامل بسياسة البناء والبيئة المعتمدتين **بعد تعليمات المستخدم** | فحص الحمولة والإصدار وNode/PG والترحيلات دون مفاتيح خاصة |
| 5 | تثبيت معزول، ونسخة أمان، ثم اختبارات التشغيل والاسترجاع والخدمات الأساسية | دليل مثبت لا مجرد نجاح التجميع؛ لا بيانات حقيقية قبل إغلاق مخاطر السلامة |
| 6 | استكمال بقية P1 وقبول المستخدم والتطويرات P2/P3 في الترتيب المعتمد | إغلاق البنود الـ38 في الجدول، وليس إدعاء انتهائها لتسريع التسليم |

لا توجد حاجة تقنية عامة إلى انتهاء كل تحسين شكلي قبل بناء تطبيق للتجربة، لكن لا يجوز تسليم استخدام مالي/مخزني حقيقي على أنه آمن قبل حسم P0.

### ما يُختبر بعد التثبيت بدل تعطيل كل العمل

- تسجيل الدخول وتغيير كلمة المرور والخروج وانقطاع الشبكة على جلستين، وهوية الإصدار في «حول» و/health.
- ظهور مجموعات المخازن والباركود وعدم التجمد، وصورة المستخدم وشعار الشركة، والتمرير وحفظ المسودات.
- اختيار JSON/DUMP/KAYANBACKUP من جهاز Windows، واستعادة بيانات A بعد تغييرها إلى B، ثم إعادة الدخول وإعادة التشغيل والتحقق مباشرة من DB.
- خدمات PostgreSQL وBackend بعد الإقلاع، والعمل دون إنترنت، وصلاحيات مجلدات النسخ/الرفع وسلامة control schema.
- الاستلام/الصرف/التحويل الجزئي والطريق والفروق والطباعة، والنسخ المستقلة وExcel وفق الصلاحيات.
- الترقية مع الاحتفاظ بالبيانات؛ ثم خيارا الإزالة على تثبيت تجريبي: الاحتفاظ بالبيانات، أو حذف KAYAN فقط بتحذير وتأكيد، بما يشمل خدماته وبياناته ونسخه وسجلاته دون ملفات الغير.
- انقطاع العملية وفقد الطاقة/إعادة التشغيل وخطر replay للنسخة الوقائية. فحص المسارات الآلية لا يغني عن التشغيل الفعلي.

### البناء على D وإعادة استخدام الكاش

هذه مسارات اتفاق المستخدم السابقة؛ لم يُفحص جهاز Windows في مهمة التقرير:

| الغرض | المسار |
|---|---|
| مصدر البناء القياسي | `D:\KAYAN-Windows` |
| كاش مثبتات Node/PG/VC++ | `D:\KAYAN-BUILD\downloads-cache` |
| كاش npm | `D:\KAYAN-BUILD\npm-cache` |
| كاش Pub | `D:\KAYAN-BUILD\pub-cache` |
| الملفات المؤقتة | `D:\KAYAN-BUILD\temp` |

السكريبت الحالي يدعم DownloadsCache/NpmCache/PubCache. تُراجع الإصدارات والبصمات ويُعاد استخدام الملفات الصحيحة، ويُحفظ أي تعديل محلي سابق لآلية الكاش. لا يُنفذ flutter clean أو تنزيل SDK/المثبتات من جديد روتينيًا. لا يُخلط مجلد بناء قديم أو Setup سابق مع SHA المرشح الجديد.

## 9. استكمال مقترح عند صدور تعليمات جديدة فقط

1. جولة قصيرة لحسم ملاحظات إبطال/تزامن الجلسات وP0 للصلاحيات في المسارات التي ستدخل التجربة.
2. تثبيت مسار بناء تطبيق Windows من نفس SHA؛ لا إعادة تدقيق طويلة لما ثبت، ولا استخدام مسار Windows build only المسمى خطأ دون معالجة الاستدعاء القديم في مهمة مصرح بها.
3. تجربة P1 الأساسية: المستخدم/الإسناد والمخازن والمواقع والأذون والتحويل والباركود والأسعار الفارغة. يُستكمل الناقص الفعلي، ولا يعاد بناء الوظائف الموروثة الناجحة.
4. تحضير البناء بكاش D والسياسة الحالية بعد تعليمات المستخدم، ثم تثبيت معزول وقبول الحد الأدنى.
5. إغلاق بقية P1 ثم P2، وأخيرًا الانحدار الشامل والأداء الذي يتعلق بالتجمد والتزامن والتكرار، دون أهداف أو وظائف جديدة.
6. نشر/تسليم Installer نهائي يحتاج الموافقة الصريحة؛ لا merge أو تغيير Cloud/التراخيص/عروض الأسعار.

**حالة التوقف:** حفظ وتقرير فقط. لا مهمة تطوير تالية بدأت، ولا اختبارات/بناء جديدة طُلب تشغيلها. أي استكمال ينتظر تعليمات المستخدم.
