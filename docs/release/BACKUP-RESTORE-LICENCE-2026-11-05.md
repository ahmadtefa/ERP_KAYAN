## تنفيذ هذه الجولة

1. اكتُشفت حالة غير مربوطة: إذا غاب `licenseId` من الحالة المحمية مع بقاء watermark مدة أو مقاعد، كان `reconcile` يستطيع نسبتها لسجل قاعدة آخر. أضيف رفض `LICENSE_STATE_ID_MISMATCH` قبل نسب المدة أو المقاعد، مع إبقاء الطرفين كما هما. قد يحتاج مستخدم بحالة قديمة غير مربوطة لاستعادة أو انتقال معتمد؛ لا تُحذف حالته ولا يطبق عليه ترخيص بديل تلقائيًا. ثلاثة اختبارات وحدة فشلت قبل الإصلاح ثم نجحت. أضيف اختبار PG معزول لا يوقّع مفاتيح. لا يحل فقد الهوية عندما لا توجد watermark، أو rollback لكل ملفات الجهاز، أو صحة التوقيع والإلغاء.
2. لم تعد الواجهة تعرض زر الرفع أو زر استعادة ملف عند غياب capability كاملة أو false، أو عند فشل تحديثها، وتُبقي التحذير بالعربية/الإنجليزية والتنزيل. ليس ذلك بروتوكول idempotency: قبل تفعيل أي استعادة مستقبلية يلزم operation ID دائم واستعلام حالة موثوق بعد المهلة/إعادة التشغيل ومنع تكرار غير مؤكد.
3. قائمة الأرشيف وفحصه عبر API يصرحان `fullBackup:false`, `includesExternalFiles:false`, `includesLicence:false`؛ قيمة `kind:full` القديمة محفوظة للتوافق وتعني كل **قاعدة البيانات** فقط. خطأ رفع dump في مسار JSON لم يعد يوجه المستخدم إلى مسار استعادة محجوب، ويخبره بحفظ الأرشيف والتواصل مع الدعم. أضيفت اختبارات HTTP/Widget وصُمم فحص PG للحقلين. لا تختبر البيانات الحقيقية.
4. Jest محلي غير موقّع: **8 مجموعات / 157 نجاحًا** باستخدام Prisma shim، وليس PostgreSQL أو typecheck. اختبار red السابق 3 فشل/25 نجاحًا عمدًا. أُدرج اختبار JSON backup ضمن CI غير الموقّع بدل الاعتماد على تشغيل محلي فقط. النتائج القطعية لـPG وFlutter وWindows هي Actions على HEAD النهائي، لا اختبار shim.

## متطلبات متبقية قبل رفع الحجب

- تعريف مكونات ملفات التطبيق وبيانات المستخدم، سياسة النسخ المتسق مع PostgreSQL، manifest/version/canonicalization وربط hash لجميع المكونات؛ مصادقة/توقيع موثوق مع دورة مفاتيح وحماية المفتاح دون إدراج مفتاح خاص بالإصدار أو المستودع. اختبارات التوقيع تحتاج VM المعتمدة؛ لا ترخيص أو مفتاح أو بيانات عميل في logs.
- تحديد مصدر ثقة مقاوم للرجوع المستقل عن الأرشيف وملفات الجهاز (أو ضمانات عتاد/خدمة مع حدود موثقة)، ومصدر إلغاء وصلاحية يمكن الوثوق بتحديثه offline. لا يمكن إثبات أحدث حالة أو معرفة إلغاء لم يُبلّغ للجهاز من نسخة أقدم وحدها.
- قبل أي كتابة: تحقق شامل وهوية/جهاز وتوقيع وتوقيت وإلغاء/sequence، scratch مستقل، نقطة استعادة كاملة متسقة ومتحقق منها، سجل مراحل durable مع fsync وضمانات filesystem، قفل بين العمليات، إيقاف دخول واستنزاف الطلبات وإغلاق اتصالات DB، حماية بدء التشغيل والعمليات الخلفية وإعادة الدخول. لكل خطوة وخطوة rollback تعريف تعافٍ متكرر idempotent من crash، بما في ذلك فشل rollback نفسه؛ لا تحرير للصيانة بمجرد الوصول لمرحلة غير موثقة.
- تصميم وربط Repair وWindows service والملفات/ACL والأدوات المضمنة، وعدم لمس بيانات أو ترخيص العميل خلال repair، ثم تنفيذ اختبار Windows 10 وبعده 11، power-loss/restart وoffline/fresh/upgrade/repair/restore/restart/LAN في VM معتمدة. بناء Windows وحده ليس تثبيتًا أو دليلًا لاستعادة عميل.
- بعد التنفيذ يلزم اختبار جميع صفوف الجدول وقياس حالة DB والملفات والترخيص والصيانة والفقد على HEAD واحد، ثم مراجعة Release Gate بصورة مستقلة. لم يُبنَ Setup ولم ينشر إصدار أو يُدمج PR.
