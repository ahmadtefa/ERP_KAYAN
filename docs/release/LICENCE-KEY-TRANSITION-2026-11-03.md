# انتقال مفاتيح الترخيص — قرار موثّق، غير مطبّق على المنتج بعد

أقرّ المستخدم مفتاح Ed25519 العام الجديد للتراخيص الجديدة. أُضيفت نسخة عامة فقط باسم `distribution/windows/public-key-next.pem`، وحُسب SHA-256 من ترميز SPKI DER للملف الفعلي. **لا يحتوي هذا الملف على مفتاح خاص ولا يوقّع شيئًا.**

| الدور | البصمة الكاملة SHA-256 لـSPKI | الوضع الحالي |
|---|---|---|
| التحقق القديم | `9153e15e475ba2e2251a7e40d8eb58559006bbba2923ee8ba564d8d59cc602c4` | `distribution/windows/public-key.pem`، ما زال يستخدمه مسار Windows الحالي؛ لا يجوز حذفه |
| الإصدار الجديد الذي أقرّه المستخدم | `f93238b0cdc0a81d345f160cf8dcdbb7de5e4d20fa99959b7e4b165ac1ebb5c3` | `public-key-next.pem`؛ مطابقة البصمة مثبتة، لكنه **غير موصول بعد** بمسار المنتج/المثبت/الاستعادة |

`node --require ./scripts/ci-no-signing.cjs --test scripts/license-public-key-transition.test.mjs` يفحص الملفين والبصمتين ونوع المفتاح فقط؛ ليس اختبار توقيع أو إصدار أو ترخيص. أُضيفت نواة `PublicLicenseKeyring` منفصلة تشترط البصمتين الكاملتين وتجرّب المفتاح الثاني فقط بعد رفض توقيع الأول؛ ليست موصولة بخدمة المنتج. اختبارها يستخدم mock للتحقق ويختبر التحكم والبصمات دون توليد أو توقيع أو تحقق توقيع حقيقي؛ نجاحه ليس دليل توافق التراخيص.

## ما يمنع التبديل الآن

- الخدمة تحمل مفتاحًا واحدًا وتربطه ببصمة محفوظة محمية، ثم تتحقق منه قبل الطلبات والعمليات. استبدال الملف وحده يحجب تثبيتًا قائمًا أو يكسر التراخيص القديمة؛ لا تُغيّر البصمة المحمية تلقائيًا.
- بناء Windows وسياسة البناء وأدوات إصدار سطح المكتب لا تزال تعتمد المفتاح القديم في مواضع مختلفة، بينما مولّد Android يذكر البصمة الجديدة. لم يثبت وصول حلقة مفاتيح متوافقة إلى Setup أو إصداره.
- إثبات التوقيع المحفوظ لا يدخل مسار الاستعادة الإنتاجي بعد. حالة الإلغاء/القيم غير المعروفة ومسارات الساعة والتجديد والنقل تحتاج إغلاقًا متسقًا ومقاومًا للسباق، وليس اختبارًا لمفتاحين فقط.
- لا يُستخدم المفتاح القديم لإصدار تراخيص جديدة وفق القرار، لكن فرض هذا القرار آليًا في كل مولد **لم يكتمل**؛ لا يُستخدم مولّد حالي لإصدار إنتاجي حتى تعديل السياسة وإثبات التوافق. لا تُطلب أو تُنسخ المفاتيح الخاصة.

## شروط التنفيذ قبل Setup

1. تصميم keyring مثبت بالكامل يربط كلاً من المفتاحين ببصمته ويسمح بالتحقق القديم والجديد مع فشل مغلق عند تلف أي حالة لازمة، دون ترقية صامتة للمفتاح المحمي أو قبول مفتاح اعتباطي.
2. فصل سياسة الإصدار التي تسمح بالجديد فقط عن سياسة التحقق التي تحتفظ بالقديم؛ ترحيل سجل المولّد وحفظه دون حذف أو إبطال التراخيص.
3. توصيل التحقق الموقّع بسجل الترخيص والاستعادة الذرية، مع الإلغاء والمدة والجهاز وساعة النظام وسياق الطلبات المتزامنة.
4. إثبات التوافق وقبول القديم والجديد ورفض التوقيع والجهاز والانتهاء والإلغاء باستخدام مفاتيح اختبار داخل VM المعتمدة فقط، ثم فحص محتوى المثبت ومسار التشغيل الفعلي. لا تُجرى اختبارات توقيع في CI العام أو هنا.
