## 1. المشكلة الأصلية

كان `SalesInvoicesService.post()` يخصم الكميات من **رصيد الفرع المجمّع** (`stock_balances`) مباشرةً، دون أن يمسّ الدفعات (`item_batches`) إطلاقًا. النتائج المترتّبة على ذلك:

1. **الدفعة لا تُستهلك.** تُباع الفاتورة ويبقى `remainingQuantity` في كل دفعة كما هو، فيتعارض رصيد الدفعات مع رصيد الفرع، وتصبح تقارير الصلاحية والدُفعات أرقامًا لا معنى لها.
2. **لا FEFO إطلاقًا.** لا يوجد في مسار البيع أي اختيار للدفعة الأقرب انتهاءً؛ فمن يبيع يجب أن يعرف هو — أو لا يهمّه — من أين خرجت الكمية.
3. **الصلاحية غير مفروضة.** لا شيء يمنع بيع دفعة انتهت صلاحيتها؛ لا منع ولا اعتماد ولا أثر.
4. **العكس غير مرتبط بالمصدر.** `reverse()` كان يعيد الكمية إلى الرصيد المجمّع، فإلغاء فاتورة بعد بيع دفعة أخرى كان يُنتج كميات في «لا مكان» من ناحية الدفعات، أو يعيدها إلى دفعة خاطئة.
5. **لا أثر تفصيلي.** لا يعرف أحد بعد البيع أي دفعة خرجت ولأي عميل وبكم.

## 2. المسار قبل وبعد

### قبل

```
post()
 └─ SELECT stock_balances ... FOR UPDATE        (رصيد الفرع فقط)
 └─ إذا كفى: stockBalance.update { decrement }  (خصم مجمّع)
 └─ stockMovement.create (بلا batchId)
 └─ journal posting
```

### بعد

```
post()
 └─ SELECT stock_balances ... FOR UPDATE        (فحص أولي، يبقى)
 └─ batches.issueTx(tx, ...)                    ← المسار الوحيد للصرف
     ├─ قراءة دفعات الصنف في الفرع/المخزن
     ├─ حراسة الصلاحية: هل الدفعة منتهية؟ هل يوجد اعتماد؟
     ├─ selectLotsFefo  → الأقرب انتهاءً أولًا، مع تجزئة السطر على عدة دفعات
     ├─ UPDATE item_batches SET remaining -= n WHERE remaining >= n  (شرطي)
     ├─ إغلاق الدفعة إذا فرغت (status = CLOSED)
     ├─ stockMovement.create — صف لكل دفعة (batchId مملوء)
     ├─ ledger.post — يحرّك رصيد المخزن والفرع معًا
     └─ audit: ISSUE_BATCH مع الدفعات والكميات ومن اعتمد ومتى ولماذا
 └─ تثبيت تكلفة كل سطر على الفاتورة (unitCost / costTotal)
 └─ journal posting
```

والعكس:

```
reverse()
 └─ stockMovement.findMany { referenceType: 'SALES_INVOICE', referenceId: invoice.id, direction: OUT }
     ← يقرأ ما خرج فعلًا لحظة البيع، لا يعيد حسابه بـ FEFO جديد
 └─ لكل صف: item_batches.updateMany { increment } شرطي
     ├─ إن كانت الدفعة أُغلقت بالبيع تُفتح (CLOSED → OPEN)
     └─ stockMovement.create (IN) بنفس batchId ونفس التكلفة
 └─ ledger.post مرة واحدة لكل سطر (لا مرة لكل دفعة)
 └─ posting.reverse — القيد العكسي في نفس المعاملة
```

## 5. آلية FEFO

`selectLotsFefo` في `batch-policy.ts`، ودورها:

1. تستقبل دفعات الصنف في الفرع (والمخزن إن حُدّد).
2. تستبعد ما لا رصيد له.
3. تستبعد المنتهي **إلا** إذا جاء اعتماد صريح (`allowExpired`).
4. ترتّب ما بقي بـ `expiryDate ASC` ثم `receivedAt` — الأقرب انتهاءً أولًا.
5. تختار سطرًا سطرًا وتجزّئ الطلب على عدة دفعات إن لم تكفِ الأولى.
6. تعيد `expiredQuantity` منفصلًا حتى يُسجَّل في التدقيق كمًّا وليس كعلم منطقي.

**الأمان ضد التزامن:** كل خصم دفعة يجري بـ

```sql
UPDATE item_batches
   SET "remainingQuantity" = "remainingQuantity" - $n
 WHERE id = $batch AND "remainingQuantity" >= $n
RETURNING id
```

فإن كان صفان يتنافسان، ينجح أحدهما ويُرجَع `count = 0` للآخر فيرفع الصرف خطأً بدلًا من أن يجعل الدفعة سالبة. الاختبار السادس في `sales-batches` يُثبت أن الطلب المكرّر لا يأخذ أكثر مما تتحمّله الدفعة.

## 6. معالجة الصلاحية المنتهية

**المنع افتراضيًا.** لا شيء في جسم الطلب يُفعّل الصرف المنتهي.

| الطبقة | ما تفعله |
|---|---|
| DTO / جسم الطلب | لا يوجد فيه `allowExpired` إطلاقًا — فقط `expiredIssueReason?` نصّي |
| `sales-invoices.controller.ts` | يحسب `mayIssueExpired` من `user.isSuperAdmin` أو من الصلاحية `inventory.batches.expired.issue` الموجودة فعلًا في قاعدة الصلاحيات |
| `sales-invoices.service.ts` | يبني `expiredApproval = { userId, reason }` **بعد** فحص الصلاحية، ويُمرّره داخل `IssueInput` |
| `batches.service.ts` (`issueTx`) | إن جاء `allowExpired` بلا اعتماد صالح → `ForbiddenException` |
| سجل التدقيق | يُكتب `expiredApproval` مع `approvedBy` و`reason` و`decidedAt` و`expiredLots` و`reference` |

**نصّ الرسالة:** «صرف صنف منتهي الصلاحية يتطلب اعتمادًا مسجّلًا بصلاحية وسبب. / Issuing expired stock needs the expiry-issue permission and a recorded reason.»

**نقطة فرض واحدة.** `issueTx` هي الدالة التي يمرّ بها كل صرف (بيع، تحويل، إتلاف، جرد)، فالحارس فيها يمنع الالتفاف عبر أي مسار آخر.

**ملاحظة صريحة يجب أن تُقرأ:** الحارس يعمل عندما يكون `input.allowExpired === true` صراحةً. أما إذا كان الصنف نفسه مهيّأً بـ `allowExpiredIssue` في سياسته، فالسياسة تسمح والصرف يمرّ دون السجل. هذا مقصود: سياسة الصنف قرار إداري دائم، لا استثناء لحظي يحتاج اعتمادًا لكل فاتورة. لكنه يعني أن تغيير سياسة الصنف من الشاشة يفتح الصرف المنتهي بلا اعتماد. لم أغلقه لأن إغلاقه يغيّر سلوك أصناف قائمة عند عملاء حاليين. **مذكور هنا كقيد مفتوح في القسم العاشر.**

## 7. العكس والمرتجعات

**المبدأ:** الإرجاع إلى المصدر بالاسم، لا إلى «المخزن» كمتوسط.

1. `reverse()` يقرأ حركات الصرف الأصلية بـ `referenceType='SALES_INVOICE'` و`referenceId=invoice.id` و`direction=OUT`. هذه هي السجلات التي قرّرت FEFO وقت البيع، وهي المرجع الصحيح لأن دفعة قد تكون أُغلقت بعد ذلك.
2. لكل حركة: `itemBatches.updateMany({ increment })` شرطي — إن لم تُعد الدفعة موجودة، خطأ صريح لا رصيد مجهول.
3. **الدفعة المغلقة تُفتح:** أُغلقت لأن البيع أفرغها؛ فالبيع يُلغى ويجب أن تُفتح، وإلا فقدت الكمية.
4. **لا ازدواج:** `salesInvoice.updateMany({ where: { status: POSTED } })` شرطي — أول عكس ينجح، والثاني يجد `count = 0` فيرفض. الاختبار يُثبت أن الكمية لا تتضاعف.
5. **لا عكس جزئي:** الحارس على فاتورة لها مرتجع مرحّل يرفض العكس، وعلى دفعة مفقودة يرمي خطأً — فلا تبقى حركات ورصيد غير متوافقين.
6. **الذرّية:** إعادة الدفعات + الحركات + `posting.reverse` (القيد العكسي) + سجل التدقيق كلها داخل `$transaction` واحد.

## 9. العيوب المفتوحة

**لا أستطيع الادّعاء أن كل ما طُلب مبرهن.**

1. **التزامن بين اتصالين لم يُبرهن.** PGlite عملية واحدة، فلا يوجد تنافس حقيقي على قفل صف. ما بُرهن: أن `UPDATE ... WHERE remaining >= n RETURNING` شرطي فعليًا وأن الدفعة المطلوبة مرتين لا تُصرف مرتين. **ما لم يُبرهن:** أن فاتورتين تُرحَّلان في اللحظة نفسها من اتصالين تتصرفان كما هو متوقّع. يحتاج هذا خادم PostgreSQL حيًّا. الحارس نفسه يسجّل هذه الحقيقة: «PGlite exhibits no cross-session FOR UPDATE blocking».
2. **`@electric-sql/pglite` اعتماد تطوير جديد.** لم يكن موجودًا. أُضيف إلى `devDependencies` وحده؛ لا يمسّ وقت التشغيل. بيئة اختبار لا تعتمد على شبكة/xvfb.
3. **سياسة الصنف نفسه** (القسم 6): صنف مهيّأ `allowExpiredIssue` يُصرف منتهيًا بلا اعتماد. مقصود، لكنه ثغرة إدارية محتملة كما ذُكر.
4. **Flutter لم يُشغَّل ولا مرة.** 605 حالة مكتوبة، 0 منفّذة — لا SDK في هذه البيئة. كل ما في هذا التقرير Backend.
5. **تاريخ الكوميتات:** القسم في أعلى التقرير.
