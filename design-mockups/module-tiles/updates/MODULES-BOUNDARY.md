# المشتريات والمخزون — وحدتان مستقلتان

> هذا الملف فصل بين **ما هو موجود فعلاً في الكود**، و**ما هو موجود في الـ API بلا واجهة**، و**ما هو مقترح تصميماً فقط**.
> المصدر: قراءة `lib/app/shell/erp_shell.dart` (شجرة التنقّل الحالية)، و`lib/features/**`، و`backend/src/modules/purchases`، `backend/src/modules/inventory`، `backend/src/modules/returns`.
> لم أشغّل التطبيق ولم أختبر أي شاشة؛ الحالات أدناه مأخوذة من قراءة المسارات والشاشات.

---

## 1. الحكم المختصر

- **المشتريات** تملك **المستند**: فاتورة شراء، مردود شراء، أمر شراء. أي مستند يمسّ المورد أو السعر أو الضريبة يخصّها.
- **المخزون** يملك **الأثر**: الرصيد، الحركة، المخزن، التحويل، التسوية، الجرد. أي رقم يمسّ الكمية أو مكانها يخصّه.
- **الترحيل** هو الجسر الوحيد: فاتورة الشراء المرحّلة تُنشئ حركة استلام في المخزون.
- **المخزون لا يُنشئ مستند شراء أبداً**، والمشتريات لا تعدّل رصيداً بنفسها.
- هذا الفصل **لا يعني الدمج**: الوحدتان تظهران كبلاطتين منفصلتين بلونين مختلفين (أخضر وأورانجي)، ولهما تبويبات وشاشات مستقلة.

## 3. كيف يظهر «المستند يُنشئ الحركة» بلا دمج

في تصميم هذه الحزمة (الملفان `05` و`07`):

1. **في المشتريات:** بطاقة «الربط بالمخزون» تقول صراحةً: «ما ينتج عن ترحيل الفاتورة»، وتعرض مخزنين وكمية وقيمة لكل منهما، بلون المخزون (أورانجي) داخل بطاقة خضراء.
2. **في المخزون:** بطاقة «العلاقة بالمشتريات» تقول: «فاتورة الشراء `PV-2026-0071` أنشأت استلاماً في المخزن الرئيسي: 42 وحدة بقيمة 2,340.00»، ثم سلسلة مصغّرة: `أمر شراء → فاتورة شراء → استلام → رصيد` — الخطوتان الأولى والثانية بلون المشتريات، والثالثة والرابعة بلون المخزون.
3. **زر العبور** في المخزون يفتح المستند في وحدة المشتريات؛ العبور يغيّر الوحدة وليس الصفحة نفسها.

### قواعد العلاقة (تصميمية)

| القاعدة | الأثر |
| --- | --- |
| مستند الشراء يُنشئ حركة واحدة على الأكثر لكل مخزن في السطر | لا تكرار حركات |
| ترحيل الفاتورة مسؤولية المشتريات؛ عكسها يعكس أثرها | لا يُعكس الأثر من المخزون يدوياً |
| التحويل بين المخازن والتسويات والجرد تخصّ المخزون ولا تُنشئ مستند شراء | لا خلط في المسؤوليات |
| عكس سند مخزون لا يمسّ الفاتورة الأصلية | المسارَان مستقلان في التراجع |
| كل حركة تحمل مرجع المستند المصدر | تتبّع من الرصيد إلى الورقة |

## 4. الفجوات التي يجب حسمها قبل التنفيذ

1. **واجهة أوامر الشراء:** موجودة في الـ API ولا تظهر للمستخدم. هل تُضاف في المرحلة الأولى أم تُؤجَّل؟
2. **سند الاستلام:** هل يبقى أثراً داخلياً للفاتورة، أم يصبح مستنداً يُفتح ويُطبع ويُوقَّع؟ القرار يغيّر شكل وحدة المشتريات.
3. **شاشة المخازن:** الـ API يدعم إدارة كاملة، والواجهة لا تعرضها. هل تظهر كتبويب داخل المخزون أم كإعدادات؟
4. **سندات المخزون:** تحويل/تسوية/جرد مدعومة في الخادم. تصميمها يحتاج قراراً في اعتماد السند (مسودة ثم ترحيل، أم ترحيل مباشر).
5. **حالة السداد:** إن أُضيفت كحقل مخزّن فهي تغيير على قاعدة البيانات، وإن بقيت مشتقة فهي عرض فقط. التصميم يفترض الاشتقاق.
6. **الصلاحيات:** أي تبويب جديد يحتاج صلاحية جديدة أو إعادة استخدام صلاحية قائمة؛ التصميم لا يفترض صلاحيات غير موجودة.

## 5. ما لا يقوله هذا الملف

- لا يقول إن أي وظيفة «تعمل»؛ يقول إن مسارها موجود في الكود أو غير موجود.
- لا يحكم على جودة التنفيذ الحالي ولا على أداء الخادم.
- لا يقترح دمج الوحدتين ولا إلغاء أي منهما.
